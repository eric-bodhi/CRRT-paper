# CRRT itemid inventory — evidence for manual review

Generated by `uv run python -m crrt.itemid_inventory` against `data/mimiciv/3.1` (65,366 patients with an ICU stay, 94,458 ICU stays).

> **The sweep decides nothing.** Plan Part 2.3 requires that every itemid be
> eyeballed by hand — label, unit, row count, value distribution — before it is
> trusted. The sweep below is deliberately over-inclusive. The `include? / reason`
> column is copied from the hand review in `config/itemid_review.yaml`; edit
> verdicts there, never here, because this file is regenerated on every run.
> 0 candidate(s) are UNREVIEWED.

> **Small cells (Part 1.4).** Every count from 1 to 9 is shown as `<10`. Percentiles are shown as — unless at least 10 values from at least 10 stays stand behind them. Text values charted fewer than 10 times are not listed.

> **Scale.** Counts come from the database named above. A build on the demo can reject an itemid that is empty or mislabelled, but cannot show that one is representative. Lock the list from a full-database run.

## How candidates were selected

Of **4,095** rows in `d_items`, **167** are listed below. A row qualifies if *either*:

1. `category = 'Dialysis'`, regardless of label; **or**
2. its `label` **or** `abbreviation` contains any of the 39 case-insensitive substrings in `config.yaml → itemid_inventory.label_patterns`.


The `matched by` column records which rule fired. Broad patterns pull in obvious non-CRRT items — `tmp` matches Bactrim (SMX/TMP), `filter` matches ventilator filters, `renal` matches enteral formulas. Those are left in. A false positive costs one line of review; a missed itemid costs a variable.


**Recall check.** All 20 itemids in `MIT-LCP/mimic-code` `concepts/treatment/crrt.sql` are present below (marked ✔ in `concept`). The sweep also surfaces circuit items that concept does not carry — notably `229247 Trans Membrane Pressure` and `229248 Pressure Drop`, which are exactly the flow-adjusted pressure parameters Part 7 calls the differentiator.

## Evidence table

One row per itemid per numeric channel. `n rows` / `n stays` are raw counts; `n num` is how many rows carry a parseable number (0 for Text items). `units` are the distinct unit strings **observed in the data**, with counts — not `d_items.unitname`. Percentiles are p5/p50/p95 of the channel column.

`inputevents` and `ingredientevents` items appear **twice**, once for `amount` and once for `rate` — both are real channels and reporting only one would hide evidence. Items with no rows in this database are listed with `n rows` = 0.
